Default

If format is missing or unrecognized, the server mints a Snowflake. The response echoes the string you sent in its format field, even when it was empty or misspelled.

snowflake

The core package's generator, unchanged: 41-bit timestamp, 10-bit machine, 12-bit sequence, rendered in base 10. See How it works.

ulid

A 128-bit ID rendered as 26 characters of Crockford Base32 (digits and uppercase letters, without I, L, O, U).

  • 48 bits of Unix-millisecond time, then 80 bits of randomness from crypto/rand.
  • Within one millisecond the 80-bit random part is incremented instead of redrawn, so IDs from one engine stay ordered. A mutex protects this state.
  • The same millisecond can overflow the 80-bit counter only after 280 IDs, which is not reachable.

uuidv7

An RFC 9562 version 7 UUID: 48 bits of Unix-millisecond time followed by random bits, with the version nibble set to 7 and the variant bits set to 10.

Ordering

Two UUIDv7 values minted in the same millisecond are ordered randomly. They sort correctly across milliseconds but not within one. If you need strict order within a millisecond, use ulid or snowflake.

tsid

The Snowflake integer written in Base62 (0-9A-Za-z), which gives a shorter string, at most 11 characters.

  • This is not the TSID specification used by some other libraries. It is a Base62 encoding of this package's Snowflake.
  • Strings sort in time order only when they have equal length. Today's IDs are all the same length, but if you sort across a length change, compare numerically or left-pad.
  • The server cannot decode a tsid back into fields.

custom

A Snowflake-style ID with configurable field widths, stored in CustomBitConfig:

type CustomBitConfig struct {
	TimestampBits  uint8
	DatacenterBits uint8
	WorkerBits     uint8
	SequenceBits   uint8
	Epoch          int64 // Unix ms
}

The layout is timestamp | datacenter | worker | sequence, most significant first, with its own lock-free state word and the same hold-and-advance rule as the core generator. The result is an unsigned decimal.

  • The server always starts with DefaultCustomBitConfig(): 41 / 0 / 10 / 12 bits and the 2024 epoch. With zero datacenter bits, --datacenter has no effect on the ID.
  • Machine and datacenter IDs are masked to their field widths, not validated.
  • The bit widths are not checked against the 64-bit limit. A configuration whose widths sum to more than 64 produces wrong IDs.
Do not mix with snowflake

With the default config, custom uses the same layout and epoch as snowflake but a separate counter. On the same machine the two can mint the same number in the same millisecond. Keep each format in its own keyspace.

Prefixes

prefix=usr_ yields usr_374208188427300864. The prefix is plain concatenation with no validation. When decoding, the server splits on _ and uses the last part, so a prefix may contain underscores but the ID itself must not.

Decoding

DecodeID tries, in order:

  1. A positive integer: decoded as a Snowflake with the core epoch.
  2. A 36-character string with four dashes: decoded as a UUIDv7 timestamp.
  3. A 26-character string: decoded as a ULID timestamp.
  4. Anything else: returns format: "unknown" with the current time.

The machine ID reported for UUIDv7 and ULID is the server's own, because those formats do not carry one. A custom ID decodes as a Snowflake, which is only meaningful with the default layout.
