Reference implementation

The platform is a complete, tested demonstration of a multi-tenant ID service. Several parts are simulated or unauthenticated, and state is held in memory per process. Read Security model before exposing it beyond a trusted network.

Run it

snowflake serve-saas --machine 0 --addr :8080

Besides the API it serves a dashboard from the web directory. All JSON errors share one shape:

{"error":{"code":"RATE_LIMIT_EXCEEDED","message":"…"}}

Generate

GET /api/v1/ids/generate

ParameterDefaultMeaning
formatsnowflakeOne of the five formats
prefixnoneText placed before each ID
count11..100,000. A value that is not a positive integer is treated as 1; above the limit returns 400 INVALID_COUNT
$ curl 'localhost:8080/api/v1/ids/generate?format=ulid&prefix=ord_'
{"id":"ord_01K8…","format":"ulid","pod":"snowflake-worker-0","machineId":0}

$ curl 'localhost:8080/api/v1/ids/generate?count=3'
{"ids":["…","…","…"],"count":3,"format":"","pod":"…","machineId":0}

POST /api/v1/ids/batch

Same result for a JSON body {"format":"snowflake","prefix":"","count":1000}. Other methods return 405 METHOD_NOT_ALLOWED. A missing or non-positive count becomes 1.

Decode

GET /api/v1/ids/decode?id=…

Returns a DecodedID: format, raw, timestamp, millisSinceEpoch, machineID, sequence, and a human-readable bitDetails. This route needs no key and is not rate limited. A missing id returns 400 MISSING_ID. See Decoding for what each format reports.

Authentication and limits

Generate and batch routes pass through one chain, in this order:

IP blocklist403 IP_BLOCKED
→
API key401 INVALID_API_KEY
→
Velocity checkauto-block
→
Token bucket429 RATE_LIMIT_EXCEEDED
→
Handler

Send a key as X-API-Key: <key> or Authorization: Bearer <key>. Without a key the request is anonymous and limited per client IP.

CallerLimit (requests per second)
Anonymous50, per IP
free key100
pro key5,000
enterprise key100,000

Limits count requests, not IDs: one request for 100,000 IDs costs one token. Responses carry X-RateLimit-Limit and X-RateLimit-Remaining; a 429 adds X-RateLimit-Reset and Retry-After.

POST /api/v1/auth/keys

Creates a key. Body: {"tenantId":"acme","tier":"pro"}. An unknown tier becomes free; a missing tenant gets a generated name. Returns 201 with the key, shown once:

{"apiKey":"sk_live_pro_…","tenantId":"acme","tier":"pro","rateLimit":5000,"createdAt":"…"}

Only a SHA-256 hash of the key is stored. Two demo keys are created at start-up, but their values are random and not printed, so they are not usable.

What the metrics mean

  • currentRps is the IDs counted in the current plus the previous second, so it lags by up to one second.
  • Latency percentiles come from the last 5,000 generation calls (the time inside the engine, not the whole HTTP request). With no samples yet, placeholder values 1.2 / 4.8 / 12.5 µs are returned.
  • clusterNodes is sample data. The local pod appears with its real name and IDs, but CPU, memory and request figures are fixed numbers, and two more nodes are invented. Nothing polls real pods.

Cross-origin and headers

Every response allows any origin (Access-Control-Allow-Origin: *), answers OPTIONS with 204, and sets X-Frame-Options: DENY, X-Content-Type-Options: nosniff and X-XSS-Protection. The server uses 10-second read and write timeouts.
