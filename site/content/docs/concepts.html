The ID layout

Every ID is a 64-bit integer split into four fields. The top bit is always zero, so the value is a positive int64.

0bits 62..22timestamp, 41 bits21..12machine11..0sequence
FieldBitsRangeMeaning
Timestamp410 .. 241−1Milliseconds since 2024-01-01T00:00:00Z
Machine100 .. 1023Which generator minted the ID
Sequence120 .. 4095Counter within one millisecond

Three limits follow directly:

  • Lifetime. 241 ms is about 69.7 years, so IDs run out of timestamp space around 2093. The custom 2024 epoch is what buys this headroom; a 1970 epoch would already have used 55 years.
  • Machines. At most 1,024 generators can run at once without sharing an ID.
  • Rate. One machine can mint 4,096 IDs per millisecond, about 4.1 million per second, before it starts borrowing time from the future (see below).

Why lock-free

The textbook Snowflake guards its state with a mutex, and sleeps or returns an error when the wall clock moves backward. snowflake-lite avoids both. It keeps the only mutable state, the pair (timestamp, sequence), in a single atomic.Uint64:

state = timestamp << 12 | sequence     // 41 + 12 = 53 bits, fits a uint64

Generating an ID is then a read, a computation, and one CompareAndSwap. If another goroutine changed the state in between, the swap fails and the loop retries with the new value.

The algorithm, step by step

Inside Generator.Next:

  1. Load the packed state and split it into lastTS and lastSeq.
  2. Read the clock and convert it to milliseconds since the epoch (now).
  3. Choose the next pair with one branch:
    • If now > lastTS, a new millisecond has begun: use (now, 0).
    • Otherwise this is the same millisecond, or the clock went backward: keep lastTS and use lastSeq + 1.
    • If that sequence would exceed 4095, tick the logical clock forward: use (lastTS + 1, 0).
  4. Compare-and-swap the old state for the new one. On failure, go back to step 1.
  5. Assemble the ID: timestamp<<22 | machine<<12 | sequence.

When the clock moves backward

NTP corrections and VM migrations can make the wall clock jump back. The branch in step 3 handles it without a special case: the generator never lets its timestamp go below lastTS. It holds the old timestamp and keeps incrementing the sequence. IDs stay unique and strictly ascending; they simply carry a timestamp that is slightly stale until the clock catches up.

If the clock is wrong for long enough to use up 4,096 sequence numbers, the logical clock advances one millisecond at a time, as described next.

When a millisecond fills up

If more than 4,096 IDs are requested in one millisecond, the generator does not block. It moves its logical timestamp one millisecond ahead of the wall clock and restarts the sequence. IDs remain strictly ascending. Under a sustained load above about 4.1 million IDs per second, the logical clock leads the wall clock by a growing margin, and decoded timestamps run slightly ahead of real time.

What is guaranteed

PropertyHolds when

Unique across restartsThe wall clock has not gone back past the previous run's last timestamp
Note

State lives in memory. A restart forgets the logical clock. If a process dies while leading the wall clock and restarts on the same machine ID before real time catches up, it could reuse timestamps. This is rare in practice, but if you need a hard guarantee, persist or reserve a time window per machine.

Performance and contention

A single goroutine mints an ID in about 48 ns with no allocations (AMD Ryzen 7 7735HS). Under heavy contention from many goroutines on one generator, the compare-and-swap loop retries and can lose to a plain mutex in the repository's own benchmark. The benchmarks live in snowflake/snowflake_test.go and run on your hardware with:

go test -bench . ./snowflake

If you need maximum throughput on many cores, give independent goroutine groups their own generator with a distinct machine ID.
